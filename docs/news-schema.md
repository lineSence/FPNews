# База, метки времени, дубли

## Почему SQLite

Вопрос «не взять ли что-то очень быстрое, вроде кэша» решается так:

| | Что это | Память | Здесь |
|---|---|---|---|
| **SQLite** | файл на диске, работает внутри процесса; сетевого вызова нет вовсе | 20–40 МБ кэша, настраивается | **да** |
| **Redis / Valkey** | всё в памяти, отдельный процесс, доступ по сокету | 30–100 МБ плюс данные | нет: обращение через сокет (0,1–0,5 мс) медленнее вызова функции, а выигрыш появляется только когда процессов много |
| **PostgreSQL** | сервер БД, много писателей, строгие транзакции | 150–300 МБ | нет, пока пользователей десятки |
| **DuckDB** | аналитика по колонкам | — | не для горячих записей; пригодится для статистики по архиву |

Режим WAL: читатели не мешают писателю. Пишущий контур один, при сотнях
новостей в сутки это не ограничение. Горячее состояние (что видели, что
отправили) живёт в памяти процесса, база — это память между перезапусками.

## Четыре метки времени `[NEWS-001]`

На каждой новости:

| Поля | Что значит |
|---|---|
| `published_at` | время публикации по данным издания (лента, мета-тег статьи) |
| `listed_at` | когда адрес появился у нас в ленте — момент обнаружения |
| `fetched_at` | когда скачался и разобрался текст |
| `sent_at` | когда ушло сырое сообщение первому получателю |
| `enriched_at` | когда ушло дополнение (текст, выжимка, склейка) |

Из них считаются три задержки, и разделять их обязательно, потому что чинятся
они по-разному:

- **редакционная** (`listed_at − published_at`) — сколько издание держало
  новость до ленты. От нас не зависит, но задаёт потолок и должна быть видна,
  иначе мы будем оптимизировать код там, где виноват чужой CDN.
- **наша до отправки** (`sent_at − listed_at`) — единственное, что мы реально
  сокращаем.
- **до полного** (`enriched_at − sent_at`) — качество догона.

Диагностика (`diag` из FuckHR) пишет их событием на каждую новость. Отчёт по
дню — распределение, а не среднее: одна залипшая новость среднее испортит, а
медиана и девяностый процентиль скажут правду `[CORE-019]`.

## Таблицы

- `sources` — издание, дверь, интервал, состояние защиты.
- `items` — новость: канонический адрес, издание, заголовок, время публикации,
  текст, первый абзац, симхэш, метки времени.
- `item_revisions` — редакции материала: заголовок, длина текста, хэш; на них
  строятся досылки.
- `topics` — тема пользователя: слова, описание словами, пороги, источники.
- `users` — пользователь Telegram, часовой пояс, тихие часы.
- `deliveries` — что кому ушло и когда, с типом (сырое, дополнение, изменение,
  «тоже написали»). Защита от повторной отправки — здесь.
- `clusters` — сюжет: несколько материалов разных изданий об одном событии.
- `embeddings` — вектор с именем модели. Векторы разных моделей несравнимы
  `[LLM-011]`, поэтому имя хранится рядом и при смене модели старые не
  переиспользуются.

## Холодный старт

Первый заход сторожа видит всю ленту сразу — двенадцать часов чужих новостей.
Считать их «обнаруженными» нельзя: на живом прогоне 24.09.2026 это дало
медианную «редакционную задержку» в шесть часов, то есть возраст ленты, а не
скорость издания.

Поэтому у новости есть признак `cold`. Подобранное на первом заходе пишется в
базу (иначе оно тут же приедет как новое), но не попадает ни в статистику
задержек, ни в рассылку. То же правило применяется после долгого простоя.

## Дубли: два уровня

**Точный — в горячем пути, бесплатно.**

1. канонический адрес: убираем `utm_*`, якоря, хвосты вида `?from=`;
2. нормализованный заголовок: нижний регистр, `ё` → `е`, схлопнутые пробелы,
   снятая пунктуация;
3. симхэш по первым абзацам — ловит перепечатку с мелкой правкой.

**Смысловой — в обогащении, через сеть.** Эмбеддинг заголовка и первых абзацев,
сравнение с материалами за окно в несколько часов, порог близости. Работает
через секунды после отправки, и это нормально: результат уходит вторым
сообщением «тоже написали», а не задерживает первое.

Порог подбирается в сторону осторожности: склеить две разные новости хуже, чем
не склеить две одинаковые, — при ошибке склейки пользователь новость **не
увидит**, а это прямое нарушение `[NEWS-004]`.

## Досылки

Материал перечитывается с убывающей частотой: первый час часто, дальше реже,
через сутки перестаём. Поводы для сообщения «изменение в новости …»:

- изменился заголовок;
- дописан существенный кусок текста (порог по доле символов, не по любому
  пробелу);
- сменился смысл — проверяется в обогащении моделью и только если первые два
  признака сработали.

Правки самого текста без этих признаков (опечатки, теги) не шлются: иначе бот
превратится в шум.
